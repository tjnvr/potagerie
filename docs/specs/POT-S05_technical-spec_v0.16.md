## 1. Principles

- **An installed app, local first.** No hosting and no account: a single user, and the data stays on their devices.

  | Mode | Launch | Storage | Lot |
  |---|---|---|---|
  | **Development** | `cargo tauri dev`: the app opens and the interface hot-reloads (Vite server) | SQLite in the data folder of the app | — |
  | **Desktop** | `Potagerie.app` on macOS, `Potagerie.exe` on Windows | SQLite in the data folder of the app | 1 |
  | **Mobile** | iOS and Android app | SQLite in the data folder of the app | 2 |
  | **Sync** | The devices exchange their changes, merged without conflict | CRDT document | 3 |

  All modes share the same interface and the same Rust commands. Going from one to the other only changes the build target.
- **Svelte + TypeScript for the interface, Rust for the rest.** The interface is a Svelte application compiled by Vite and embedded in the app. It calls the Rust core through Tauri commands (`invoke`), whose TypeScript types are generated from Rust.
- **The business logic lives in Rust.** The calculations of dates, stages, conflicts, free slots, suggestions (S03) and the consistency rules are written in Rust and unit-tested (`cargo test`). The interface shows what Rust returns and redoes none of these calculations: the only logic on the interface side is animation and drag and drop.
- **The model is ready for merging from lot 1** (see 5), so that moving to the CRDT of lot 3 does not require rewriting everything.

## 2. Architecture

```
webview ── Svelte + TypeScript interface (compiled by Vite, embedded)
   │       diorama and timeline in SVG, animation, drag and drop
   │       typed invoke() (bindings.ts generated by tauri-specta)
Tauri app `potagerie` (src-tauri)
   ├── commands   one Rust function per action, returns the year view
   ├── plan       model, rules, date calculations (S03), view, validation
   ├── catalogue  crops.json (S02), embedded
   ├── export     timeline PNG and PDF, garden JSON
   └── store      trait ── sqlite (lots 1 and 2) │ crdt (lot 3)
```

- **No server and no network port**: the webview loads the embedded interface and talks to Rust only through the Tauri commands.
- **Everything is embedded in the app**: the compiled interface (HTML, CSS, JS), the translations and the catalogue.
- **Everything builds with the standard Rust toolchain** and Node.js for the interface. No cgo, no sidecar.

## 4. Interface

| Subject | Choice |
|---|---|
| Framework | Svelte 5 + TypeScript, compiled by Vite into a single-page application (two tabs, Garden and Plan, with no router) |
| Link with Rust | `tauri-specta` generates `bindings.ts` (functions and types) from the Rust commands and structures: a change of model breaks the TypeScript build instead of breaking the app. The file is written at launch in debug mode and by `make bindings`; it is committed, and a Rust test fails if it no longer matches the code. Each command returns `{ status: "ok", data }` or `{ status: "error", error }` (the `Result` mode of tauri-specta), with a single TypeScript type per Rust type. The exposed integers fit in a JavaScript number (`u32` at most) |
| State | The interface keeps the last year view returned by Rust. Each action calls a command, which saves and returns the updated view; the interface replaces it entirely |

The element follows the finger during the gesture; on drop, the command validates and saves the position. If Rust refuses (conflict, S03 §2), the element goes back to its place and the reason is shown |
| Crop timeline | Svelte component in SVG (`TimelineSvg`), a single image: months, one row per bed, bars by phases (hatched pots, dotted growth, full harvest: the pattern distinguishes as much as the colour), dotted slots. It loads the view of the visible years (`view_year`) and merges the plantings. Scrolling and zoom (wheel with Ctrl, pinch); opens on 12 months, 6 months under 560 px. | Timeline export | The interface serialises the SVG of the timeline (`serializeTimeline`, `front/src/lib/timeline/exportSvg.ts`): a standalone SVG, with no CSS, no style, no variable and no external resource, with the font names `Figtree` and `Fredoka`, validated by a test of `crates/export`; Rust converts it to PNG (resvg, at twice the size) or to PDF (svg2pdf), with the fonts embedded in the app, then writes it to the chosen path |

| Translation | All the texts of the interface come from message files (`front/messages/en.json` is the base, `fr.json` its translation), compiled and typed (Paraglide JS, project `front/project.inlang`, plugin loaded from `node_modules` to compile without a network). The language is the one of the system (`localStorage`, then the preferred language, then English). Returning the complete view of the year after each action keeps a single source of truth, Rust, and avoids copying the rules of S03 into TypeScript. A year view stays small (10 beds at most).

## 5. Data model

One **plan** per user, stored as **a single document**. Each action loads it, changes it, then saves it.

```
Plan
├── id, version, updated_at
├── plot: length_cm, width_cm, cell_cm (25|50|100, fixed at creation), aisle_cm
├── beds{id}: name
│   └── layouts{year}: state (absent | present), type (bed|square|mound|planter),
│                      x, y, length_cm, width_cm
│                      ← only the years in which the bed changes (S03, §7)
├── plantings{id}: crop_id, bed_id, segment_start, segment_end,
│                  mode (indoor|plants|open_ground), date (sowing or planting, S03 §2),
│                  indoor_days, after_days, duration_days (copied from the catalogue at creation, S03 §2),
│                  manual_end?
└── annotations{id}: type (note|period), date_start, date_end?,
                     bed_id? (empty = the whole garden), text, hidden
```

- 10 beds at most per year.
- The length of a bed is a whole number of cells; its width is free to the centimetre. A segment is the size of a cell (S03, §4).
- Past years: the layouts and the annotations are read-only; the plantings and the bed names stay editable (S03 §17).
- A planting references a bed by its `id`, which stays stable from one year to the next.

The app checks all these rules. The computed dates (transplanting, planting out, harvest, end not edited by hand) are not stored: they are recomputed at each view from the durations copied into the planting. A catalogue update therefore shifts no planting.

**Year view**: it is what the commands return to the interface. It is computed by `plan` (`YearView::build`) from the document, the catalogue and the date of the day, and is never stored. It contains:
- the year, the date of the day and the "read only" flag for a past year;
- the plot, or nothing as long as it is not created (first launch, E2);
- `version` and `updated_at` of the plan;
- the beds that exist that year, with their layout of the year and their number of segments;
- the plantings whose period, sowing under cover included, touches the year, with their dates and their stage of the day computed (S03 §2, §3);
- the conflicts between these plantings, the free slots of the year and their suggestions (S03 §5, §8, §9);
- for each planting, its days in pots (`pot_days`);
- for each bed, the plantings deleted if it is deleted from this year (`plantings_deleted`); for each planting, its rows and plants per row (S03 §6);
- the history: the plantings ended on 1 January of the year at the latest (bed panel, read-only);
- the annotations that touch the year, and the tasks dated in the year (S03 §11).

The view adds no rule: it assembles the calculations of `plan`.

**Rules to prepare the merge (lot 3)**:
- The collections are **maps indexed by `id`**, never ordered lists: two devices can each add an element without getting in each other's way.
- The `id`s are generated on the device (UUID v7), never assigned by a counter.
- No derived data is stored.
- The `version` field serves lots 1 and 2 only; it goes away with the CRDT.

**Storage**: in lots 1 and 2, a SQLite row holds the document serialised as JSON (serde). In lot 3, it holds the CRDT document. The `store` crate exposes a `Store` trait (`load`, `save`, `replace`, `clear`):
- `save` increments `version`, updates `updated_at` and refuses to write a plan whose `version` is not that of the database (code `version_stale`): a stale copy never overwrites a more recent one;
- the first save, at the creation of the plot, inserts the plan in version 1;
- `replace` (import) writes the received plan as it is, with its `version` and its date;
- the schema is versioned by `PRAGMA user_version` and numbered migrations, never edited once published; a database written by a more recent version of the app is refused (`base_too_recent`); a database that cannot be opened or whose document cannot be read does not stop the app: every command answers `base_unreadable`, and `erase_data` removes the damaged file (and its `-wal` and `-shm` files) and starts again, except for a database written by a newer version of the app (`base_too_recent`): it holds valid data and is never erased;
- **upgrade of former data**: migration 2 renames the column `mis_a_jour_le` to `updated_at`, and `plan::upgrade_legacy_json` renames the French fields and values of the documents written by versions 0.1 and 0.2 (`planches`, `fin_manuelle`, `pleine_terre`, `tomate`…). It runs each time a document is read from the database or from an import file, and leaves a document already in English untouched.

## 6. Synchronisation (lot 3)

**Before lot 3**, each device has its own data. The transfer is done by the JSON export and its import, which replaces the existing garden after confirmation (S01, F-CPT-3), warning if the received plan is older than that of the device. "Older" compares `updated_at`: `version` counts the writes of one device, and cannot be compared from one device to another.

The export file is a JSON envelope `{ "format": "potagerie", "format_version": 1, "plan": { … } }`. A file of another format is refused (`import_invalid`), as is a `format_version` newer than the app (`import_too_recent`). The received plan is then checked (S03 §13): refusal (`import_invalid`) if the calculations cannot read it; otherwise it is accepted as it is, with the list of inconsistencies to resolve.

**In lot 3**, the document becomes a CRDT:
- Each device keeps its copy, works without a network, and exchanges its changes with the others.
- Additions made at the same time on two devices are all kept. On a same field (position, name), the last write wins.
- **Validation after a merge**: a merged document converges, but it may break the rules of the plan. The cases are specified in S03, §13:

  | Case | Example |
  |---|---|
  | Too many beds | A bed added offline on each device: 11 beds out of 10 |
  | Orphan planting | Bed deleted on one device, planting added on it on the other |
  | Overlap | Two plantings on the same segments on the same dates |
  | Past year changed | Offline change of a year that became past in the meantime |

**Transports**, which can be combined:

| Transport | How it works |
|---|---|
| QR code over Wi-Fi | One device opens a temporary server on the local network and shows a QR code; the other scans it and the two exchange their changes. Single-use token, expiring after 5 minutes |
| Cloud folder | Each device writes only its own change file (`<device>.changes`) into a shared folder (iCloud Drive, Google Drive, Dropbox), and reads those of the others. Nobody writes in the same file |

## 7. Commands

The commands that change the plan take `year`, the displayed year, and return its view. In `bindings.ts`, their names are camelCase (`viewYear`).

| Command | Role | Returns |
|---|---|---|
| `catalogue()` | The crops of S02, without the display name (translated by the interface) | List of crops |
| `view_year(year)` | Opens a year (Garden and Plan tabs) | Year view |
| `create_plot(year, plot)` | Creates the plot, and with it the plan (E2): dimensions, cell, aisle | Year view |
| `modify_plot(year, plot)` | Dimensions and aisle; the cell no longer changes | Year view |
| `create_bed(year, type, name, x, y)` | Drops a bed from the tray at its default size (S01 F-PLN-1); the default name comes from the interface | Year view |
| `plantings_exceeding(year, id, length_cm)` | Plantings that would no longer fit if the bed were shortened (S03 §4): read-only, called before `modify_bed` to warn | List of planting ids |
| `modify_bed(year, id, name?, geometry?)`, `move_bed(year, id, x, y)`, `delete_bed(year, id)` | Plan editor (S03, §6 and §7) | Year view |
| `create_planting(year, planting)`, `modify_planting(year, id, planting)`, `delete_planting(year, id)` | Crop timeline; the durations are only copied from the catalogue at creation or if the crop or the mode changes (S03 §2). Refusals: `conflict`, `zone_outside_bed`, `bed_absent`, `manual_end_invalid`, `pot_days_required`, `occupation_empty`. `planting.date_is_transplanting`: the entered date is a transplanting, Rust stores the sowing `s = x − A` | Year view |
| `shift_planting(year, id, days)` | Drag a bar by `days` days: the entered date and the manual end shift (S03 §2, T12). Refused with `conflict` if the shifted planting is no longer valid | Year view |
| `preview_planting(id?, planting)` | Read-only, called on each input of the form E07: dates and quantities (`dates`, absent if the planting cannot be built), problems to show (code, common segments and period), zones of the shortcuts All, ½, ⅓, ¼ (`null`: greyed out) and segments taken during the period. The interface calculates nothing | Preview |
| `crops_of_season(date)` | Crops whose planting-out window contains the date (S03 §10): "in season now" | List of ids |
| `create_annotation(year, annotation)`, `modify_annotation(year, id, annotation)`, `delete_annotation(year, id)` | Notes and periods (S03 §16): past year refused, unknown bed, text of 1 to 80 characters, end of a period after its start. Hiding from the timeline is `modify_annotation` with `hidden: true` | Year view |
| `export_timeline(svg, format, path)` | PNG or PDF export of the timeline | Nothing, or an error |
| `export_garden(path)` | Full export as JSON (F-CPT-3) | Nothing, or an error |
| `read_import(path)` | Reads an import file and compares it with the plan of the device, replacing nothing | Summary: date, version, number of beds and plantings, older or not, replaces a garden or not, and `incoherences`: the list of what breaks the rules (S03 §13). An unreadable or invalid file is refused (`import_invalid`, `import_too_recent`, `file`) |
| `incoherences_plan()` | Recomputes what breaks the rules of the plan of the device (S03 §13), for the "to resolve" list kept after an import | The `incoherences` list, empty with no plan or when everything is settled |
| `import_garden(year, path)` | Replaces the garden, after confirmation (F-CPT-3). Same checks as `read_import`; the inconsistencies are kept, nothing is deleted or corrected | Year view |
| `clear_plan(year)` | "Clear the plan" (F-PLN-4): deletes from `year` and the following ones all the beds of the year, with their plantings (like `delete_bed`) and their annotations that end from 1 January. Keeps the plot, the past years and the annotations of the whole garden. Refused on a past year; with no bed, does nothing | Year view |
| `erase_data()` | Erases all the data of the app, after a double confirmation (F-CPT-4) | Nothing |

Lot 3 adds the sync commands, to detail with the lot.

**Known gaps**, to specify with the editor:
- "Undo" and "Redo" (F-PLN-6) have no command: a choice remains between a history on the Rust side (the previous documents) and inverse operations.

**Writes**: in lots 1 and 2, each device writes alone in its database and each command that changes the plan increments `version` (5). In lot 3, the changes are merged (6).

**Errors**: a refused command (conflict, too many beds, past year) returns an error and changes nothing. The error is `{ code, detail }`: `code` is a fixed value, translated by the interface (`error_<code>` in the message files); `detail` is a technical message, for the log, never shown. The codes come from:
- `plan` (`PlanError::code`): `year_past`, `too_many_beds`, `conflict`, `zone_outside_bed`…;
- `plan` for placement (S03 §15): `plot_invalid`, `aisle_invalid`, `width_invalid`, `name_invalid`, `bed_outside_plot`, `bed_overlaps`, `aisle_too_narrow`;
- the app: `plot_absent`, `plot_existing`, `case_invalid`;
- `plan` for annotations (S03 §16): `annotation_unknown`, `text_invalid`, `annotation_dates_invalid` (with `year_past` and `bed_unknown`);
- storage: `saving` (reading or writing impossible: the only case where the interface offers "Retry"), `version_stale`, `base_too_recent`, `base_unreadable` (the interface then offers Retry and the settings, whose "Erase the app data" recovers);
- validation: `planting_unknown`, `bed_existing`, `planting_existing`, `crop_unknown`, `zone_invalid`, `length_invalid`, `out_of_range`;
- files: `file`, `import_invalid`, `import_too_recent`, `svg_invalid`, `rendering_impossible`.

The complete list is the `ErrorCode` type of `bindings.ts`; a code without a translation breaks `pnpm check`.

## 13. Changes since v0.8

## 16. Characters in the export (v0.16)

The PNG and PDF are drawn with the two embedded fonts (Figtree, Fredoka). Before the rendering, `export` removes the characters they cannot draw (emoji, symbols such as `≈`, `⅓`, `✓`): they would come out as empty boxes. Latin letters with accents, the usual punctuation (`’ « » – — …`), `×`, `½ ¼ ¾`, `€` and `→` are kept. The names of beds and the notes are not changed in the garden, only in the exported file.
